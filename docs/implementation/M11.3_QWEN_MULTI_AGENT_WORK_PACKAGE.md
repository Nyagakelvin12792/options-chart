## 2. Outcome

Create a pure, deterministic TypeScript package named
`@options-chart/flow-engine` that consumes validated `MarketEventV1` records and
produces auditable order-flow features without changing production feeds, chart
behavior, options calculations, risk calculations, or execution behavior.

The package must provide:

1. aggressive buy and sell quote volume;
2. cumulative volume delta with explicit anchors;
3. rolling and candle-bucketed CVD;
4. deterministic L1 spread, midprice, microprice, and bounded L2 imbalance;
5. liquidity addition, removal, and replenishment near a reference price;
6. price-response efficiency per unit of aggressive flow;
7. pending and finalized absorption candidates;
8. rejection, acceptance, unresolved, and unavailable outcomes near supplied levels;
9. feature freshness, coverage, gap, and confidence evidence;
10. deterministic replay fixtures, audit serialization, and benchmarks.

This package is decision support, not an execution engine. It must describe
observable behavior and uncertainty, never hidden participant intent.

## 4. Authority And Time Rules

- Input must already satisfy `MarketEventV1`.
- Event eligibility during replay is determined only by
  `receiptTimestampMs <= replayCutoffMs`.
- Feature time uses `exchangeTimestampMs` when present and valid; otherwise it
  uses `receiptTimestampMs`, while preserving the selected source in audit data.
- Events must never be reordered in a way that introduces future information.
- Late events may update only outputs whose effective cursor has not already
  been finalized, unless the caller explicitly requests a deterministic full replay.
- Opaque sequence strings may be compared for equality only. Never perform
  arithmetic or ordering on them.
- Numeric sequence continuity may be evaluated only when the event contract and
  source provide sufficient evidence.
- A health gap, stale state, malformed book transition, or inadequate coverage
  must lower confidence or produce unavailable output, never a synthetic value.

## 7. Calculation Requirements

### 7.1 Trade normalization

- Use quote volume: `price * quantity`.
- Preserve base quantity and quote volume separately.
- Use validated `takerSide` when present.
- `isBuyerMaker` may derive taker side only for the documented Binance Spot
  semantics and only when `takerSide` is null.
- If side remains unknown, include the trade in total-volume coverage but not in
  directional CVD. Record the exclusion count and quote volume.
- Reject or mark unavailable nonfinite, nonpositive, or overflowed decimal conversion.

### 7.2 CVD

- Raw delta is aggressive-buy quote volume minus aggressive-sell quote volume.
- Provide cumulative CVD with explicit anchor IDs and anchor timestamps.
- Provide configurable rolling windows by duration and event count.
- Provide candle buckets aligned to explicit Binance timeframe boundaries.
- A reset must create a new anchor; never silently rewrite historical CVD.
- Missing-side volume lowers directional coverage.
- Replay prefixes must produce the same prefix results as live incremental processing.

### 7.3 Order book

- Apply snapshots and deltas deterministically.
- Maintain bids descending and asks ascending without O(n squared) rebuilds per event.
- Remove a level when validated quantity is zero.
- Calculate best bid, best ask, midprice, spread amount, spread basis points,
  microprice, top-N imbalance, and basis-point-band imbalance.
- Bound retained levels and reject crossed or otherwise invalid states according
  to an explicit policy.
- Never infer a sequence gap from information the event does not expose.

### 7.4 Liquidity behavior

- Measure additions and removals separately by side and distance from reference price.
- Detect replenishment only when removed displayed liquidity returns within a
  configured time and price tolerance.
- Label replenishment as observed displayed-liquidity behavior, not an iceberg order.
- Keep cancellation/removal distinct from executed aggressive volume.

### 7.5 Response efficiency

- Measure signed price movement in basis points per unit of signed aggressive
  quote volume over versioned windows.
- Preserve numerator, denominator, window, sample count, and exclusions.
- A zero or inadequate denominator returns unavailable rather than infinity or zero.

### 7.6 Absorption

An absorption candidate requires all of:

1. elevated aggressive volume relative to a trailing, past-only baseline;
2. limited adverse price progress relative to that aggressive flow;
3. proximity to a supplied `RelevantLevelV1` active at the event time;
4. adequate trade-side and book coverage;
5. no unresolved gap or stale condition.

Buy absorption means aggressive buying fails to make proportional upward
progress near resistance. Sell absorption means aggressive selling fails to
make proportional downward progress near support.

Never call absorption proof of a hidden seller or buyer.

### 7.7 Rejection and acceptance

- A candidate begins as pending.
- It may finalize only after the configured response horizon has elapsed using
  events that were not available at candidate creation.
- Rejection requires movement away from the level plus failure to regain it
  under explicit tolerances.
- Acceptance requires sustained trade on the far side of the level for a
  configured duration and/or volume threshold.
- If the horizon ends without sufficient evidence, finalize as unresolved.
- Final records must include candidate time, finalization time, level version,
  thresholds, evidence IDs, and component scores.

## 8. Configuration And Scoring

All thresholds must live in a versioned `FlowEngineConfigV1`. No unexplained
magic numbers may appear inside calculations.

Include at least:

- CVD anchors and rolling windows;
- candle timeframes;
- book depth and basis-point bands;
- stale and gap tolerances;
- level-proximity basis points;
- trailing baseline windows and minimum samples;
- elevated-flow threshold;
- limited-progress threshold;
- response horizon;
- rejection and acceptance tolerances;
- minimum trade-side and book coverage;
- maximum evidence IDs retained per snapshot.

Component scores must remain independently inspectable. Do not collapse all
evidence into one opaque score. Any summary strength must be a relative ranking,
not a calibrated probability.

## 11. Iteration Loop

At checkpoints 2 through 6, repeat this bounded loop:

1. run the narrowest relevant tests;
2. classify failures as contract, implementation, fixture, integration, or environment;
3. assign each code failure to exactly one owning agent;
4. patch without weakening assertions or broadening scope;
5. rerun focused tests;
6. run dependent package tests;
7. ask the read-only reviewer to inspect the corrected diff;
8. update the worklog.

Continue until the checkpoint is green or a genuine blocker is documented.
Limit any unchanged failing approach to two attempts. After two equivalent
failures, stop repeating it, record evidence, and choose a different approach.

Do not loop on unavailable network access, missing credentials, quota exhaustion,
or required product decisions. Preserve the checkpoint and stop cleanly.
